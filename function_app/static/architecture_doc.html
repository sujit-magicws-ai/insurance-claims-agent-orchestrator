Durable Functions State Management

A normal Azure Function is stateless — it runs, finishes, and forgets. Durable Functions persist state automatically so orchestrations survive restarts, crashes, and long waits (like the 24-hour HITL timeout).

How It Works: Event Sourcing

The framework doesn't store a snapshot of "current state". Instead it records a history of every step that happened — every activity call, every timer, every external event. This is called event sourcing.

#History EventStored Result
1Orchestrator startedInput payload (claim_id, email, PDF URL)
2call_activity("agent1_activity")Classification output
3call_activity("notify_activity")Notification result
4wait_for_external_event("ManualEstimate")(paused — no result yet)
5External event receivedReviewer's estimate data
6call_activity("agent2_activity")Adjudication decision
7call_activity("agent3_activity")Composed email
8Orchestrator returnedFinal result dict

The Replay Mechanism

When the orchestrator wakes up (e.g. after an external event arrives), the framework replays the entire function from the top. But it doesn't re-execute activities — it sees the result already in the history and returns it instantly. Real work only happens when it reaches a new step not yet in the history.

That's why the orchestrator guards log statements: if not context.is_replaying: logger.info(...) — so logs only fire once, not on every replay.

Three Kinds of State

KindWritten ByRead ByLifetime
History Framework (automatic) Framework (replay) Every yield result is saved. You never manage this.
Custom Status context.set_custom_status({...}) client.get_status(id).custom_status Overwritten on each call. Only the latest value is visible. Acts as a live progress whiteboard.
Final Output return result client.get_status(id).output Set once when the orchestrator finishes. Includes the full result dict with all agent outputs, timestamps, and decision.

Where State Is Stored

WhatWhereYou Manage It?
Event historyAzure Storage (tables + queues + blobs)No — automatic
Custom statusInside the historyYes — set_custom_status()
Final outputInside the historyYes — return value
Activity inputs/outputsAzure Storage queues & blobsNo — automatic

Locally, Azurite emulates Azure Storage in Docker. Restarting the Azurite container clears all state (in-memory only).

Orchestrator Code Constraints

Because of replay, orchestrator code must be deterministic. If code runs differently on replay vs. first execution, the history won't match and the framework will error.

Don't Do ThisDo This InsteadWhy
uuid.uuid4() context.new_guid() Random values differ on replay
datetime.now() context.current_utc_datetime Time changes on replay
await some_api() yield context.call_activity(...) I/O must go through activities to be recorded
logger.info(msg) if not context.is_replaying: logger.info(msg) Avoid duplicate log entries
